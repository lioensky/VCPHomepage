## 最新更新

### 2026-08-30 · 系统级语音交互、渲染态流式朗读与 Electron 44 升级

本次更新集中重构 VChat 的语音输入、语音生成与流式朗读链路，并同步升级桌面运行时。语音交互不再局限于 VChat 窗口：用户现在可以在游戏、创作软件及其它第三方应用中直接通过麦克风与 Agent 协作，形成从系统输入、Agent 理解到界面操作的完整闭环。

#### 系统级语音输入与 Rust 独立引擎

旧版语音输入依赖 Puppeteer 驱动浏览器会话，再通过代理链路调用 Gemini Web 页面内的语音识别能力。这种方案需要同时维持浏览器进程、页面运行状态、代理转发与 Web 服务连接，不仅链路较重、资源开销较高，也容易受到页面变更、会话失效、浏览器状态及网络波动影响，长期运行时稳定性不足。

新版已移除这条基于浏览器自动化的间接链路，改为直接调用系统语音 API。语音采集与识别不再需要启动和托管 Gemini Web 页面，从而减少中间进程、代理转发与页面依赖，降低输入延迟和故障点。

新增基于 Rust 的独立语音输入引擎，可监听程序内可用麦克风，并通过以下两类通道完成语音识别与输入：

1. **Windows 原生通道**：通过 WinAPI 接入系统级语音能力。
2. **输入法本地通道**：若用户电脑已安装豆包输入法客户端/讯飞输入法客户端，即可直接调用 Doubao API/讯飞 API，无需另行配置云端语音服务。

该引擎使语音控制能力可以脱离 VChat 主窗口运行。用户可在游戏中使用手柄麦克风与 Agent 交流，也可在大型专业软件中直接通过语音下达任务；结合既有 **VCP-SOM** 界面感知与操作能力，VCP 由此打通“语音指令—Agent 理解—第三方软件操作—结果反馈”的系统级交互闭环。

#### 流式朗读与本地语音推理优化

1. **渲染态流式音频解析朗读**：新增面向渲染状态的流式音频解析与播放能力。Agent 回复可以在内容持续生成和渲染的同时进入朗读管线，减少等待完整回复后再开始播放的停顿。
2. **本地 SoVITS 推理优化**：重构本地 SoVITS 推理流程，优化任务调度、缓存命中与队列管理，改善连续请求和多段语音生成时的吞吐、等待时间与资源稳定性。
3. **前端语音体验统一优化**：进一步整理语音输入、生成、缓存和播放之间的状态衔接，减少重复处理、播放迟滞及队列堆积。

#### Web 语音供应商与生成模式升级

Web 语音供应商由 Index 2.5 切换为 **Mimo 2.5**，并统一支持三种语音生成模式：

- **默认语音**：直接使用预设音色完成快速朗读。
- **克隆语音**：基于参考声音生成对应音色。
- **自然语言提示语音**：通过自然语言描述音色、语气、情绪与表达方式，无需手动调整复杂参数。

#### Electron 44 与桌面运行效率提升

VChat 的 Electron 底层依赖由 v37 迁移至 **v44**，进一步提升桌面端的安全性、稳定性和运行效率。在家用 i7 测试环境中，当前版本性能基线为 **LCP 0.6 秒、CLS 0.01、INP 8 毫秒**；程序启动速度提升约 **35%**，内存占用再次下降约 **10%**。

#### 墓碑冻结 V2 扩展潜在动画识别范围

墓碑冻结 V2 升级动画识别规则，不再只依赖显式动画声明与常规计时器特征，而是扩大对隐式、延迟触发及间接驱动动画的检测范围。更多隐藏在复合样式、脚本调度、状态变化和动态节点中的潜在动画类，现在也能被纳入生命周期追踪。

当相关内容离开可视区域时，系统可以更完整地冻结其动画帧、计时任务与关联活动；重新进入视野后再按状态恢复，减少遗漏动画在后台持续运行造成的 CPU、GPU 和内存开销，并提升超长、多动画聊天上下文的长期运行稳定性。

#### Chat Core 竞态防御与流式一致性检查

新的 Chat Core 进一步强化高并发、跨话题和多界面场景下的竞态防御，并新增三类一致性检查：

1. **状态投影一致性检查**：持续核对 Chat Core 内部运行状态与各聊天 Surface 可见投影之间的对应关系，避免旧状态、迟到事件或错误投影覆盖当前消息画面。
2. **涟漪渐进渲染队列序列化检查**：检查渐进渲染任务的入队顺序、执行代次和提交边界，阻止同一消息的旧渲染任务越过新任务写入 DOM，降低乱序推进、重复渲染和局部回退。
3. **流式状态跨域一致化检查**：统一校验流式会话在 Chat Core、消息渲染器、话题运行态及不同窗口或 Surface 之间的身份、代次与结束状态，减少跨域传播过程中出现状态分叉、重复结束或终稿不一致。

这些检查进一步收紧了消息接收、状态投影、渐进渲染和终稿提交之间的时序边界，使 Chat Core 在高速输出、话题切换、窗口迁移和迟到异步事件同时发生时仍能维持单一、可验证的流式状态。

#### 界面细节与插件阅读体验

1. **文本分行与缩放稳定性优化**：进一步改善标点符号位于段尾分行位置时的排版表现，并修复手动拖拽窗口边角缩放时可能出现的局部界面抖动。
2. **插件 README 快速阅读**：后端插件中心新增 README 快速阅读入口，用户无需离开插件管理流程，即可查看插件说明、配置方法与使用文档。

> **这次升级让语音不再只是聊天窗口中的附加输入方式，而是成为可以贯穿第三方软件、系统操作与 Agent 协作的通用交互入口；配合流式朗读、SoVITS 推理优化、Electron 44、墓碑冻结 V2 动画识别扩展及 Chat Core 一致性检查，VChat 的语音体验、渲染可靠性与桌面运行基础同步完成了一轮系统性提升。**

### 2026-08-26 · VCPMessageRenderer V4 极端内容防御与 CursorGen 跨平台指针主题生成

本次更新继续围绕复杂生成内容的安全渲染与 Agent 系统级创作能力扩展展开。前端进一步强化 VCPMessageRenderer V4 在极端、非规范 HTML 输入下的边界识别与竞态适应能力；后端则为 HtmlMediaRendererGen 新增 CursorGen，使 Agent 可以直接生成并安装跨平台鼠标指针主题。

#### V4 渲染引擎增强极端压测适应性

VCPMessageRenderer V4 完成新一轮极端内容压力测试与防御加固，重点修复恶意、错误或高度混淆的 HTML 结构可能引发的作用域误判、嵌套破坏与竞态问题。

1. **无关 Div 字段干扰防御**：当有效 `div` 区块内部混入大量错误、无关或故意制造歧义的 `div` 字段时，渲染器仍能识别真实结构边界，避免局部内容扰乱消息整体布局和流式状态。
2. **HTML 注释内容隔离增强**：注释中的脚本片段、伪标签与恶意可执行内容不会被误识别为真实页面结构或进入执行链路。
3. **破坏性占位符防御**：增强对注释、标签及嵌套结构中异常占位符的识别与隔离，降低未闭合标记、伪造边界和嵌套污染对渲染树的影响。
4. **极端输入竞态治理**：针对上述异常结构同时出现在流式增量、终稿切换和富内容处理阶段的情况，进一步收紧解析代次与渲染边界，减少旧任务和错误中间态干扰最终画面。

#### CursorGen 打通鼠标指针主题生成与安装

后端 HtmlMediaRendererGen 新增 **CursorGen** 能力。Agent 现在可以根据自然语言需求一次性生成 Windows 与 macOS 可用的鼠标指针主题包，并支持自动化安装。

这项能力将指针图形设计、不同交互状态适配、平台格式封装与系统安装串联为完整工作流。用户无需手动绘制、转换文件或逐项配置系统指针，即可让 Agent 为电脑创作并替换整套鼠标指针主题，进一步扩展 VCP 从界面内容生成到操作系统个性化资产生产的能力边界。

> **V4 渲染器继续把非规范内容约束在可靠边界内；CursorGen 则让 Agent 从生成网页与多媒体素材，进一步走向可直接安装的系统级视觉资产。**

### 2026-08-24 · TagMemo Checkpoint 自检、OneRing 长上下文遍历与前端可靠性升级

本次更新同步增强记忆资产重建、统一上下文一致性检测、恶劣网络流式渲染、消息样式隔离及工具变更审计能力，重点提升复杂生产环境中的数学可靠性、长上下文性能与人工审核效率。

#### TagMemo 资产重建 Checkpoint 自检加固

后端进一步加固 TagMemo 资产重建 Checkpoint 算法的自检能力，完善资产变化过程中的增量与减量计算校验。系统会更严格地核对变更前后状态、Checkpoint 代次及增减量关系，降低高频写入、删除或重建过程中因计数漂移造成资产不一致的概率。

新的自检与计算路径在提高数学可靠性的同时，减少了不必要的重复训练和全量重算，使模型训练与资产恢复过程更快、更稳定。

#### OneRing Hash 遍历模式增强

OneRing 的 Hash 遍历模式完成算法优化，大幅提升超长上下文中的一致性检测速度。面对跨客户端、跨会话及大量历史消息组成的上下文时，系统可以更高效地定位内容变化、顺序差异与状态偏移，减少重复遍历和无效比较，同时继续维持统一上下文事实层的可靠仲裁。

#### 流式渲染与消息样式隔离强化

1. **恶劣网络适应性增强**：进一步优化流式分包乱序、延迟、抖动、短时断联与恢复场景下的渲染推进，减少文本停顿、重复显示、局部回退及终稿切换异常。
2. **极端样式污染自动重定向**：增强 Message 气泡在极端 CSS 与结构污染测试下的自动化重定向能力。当异常样式可能越过当前消息边界时，渲染器会将相关内容重新约束到正确气泡及隔离作用域，避免影响其它消息或聊天主界面。

#### 工具变更审核新增 CodeMirror Diff 审计模态窗

通知管线现在会识别涉及文件或代码变动的工具请求。此类请求进入审核界面时，将自动提供基于 **CodeMirror Diff** 的审计模态窗，以结构化差异视图展示新增、删除与修改内容。

用户无需离开工具审核流程或手动打开目标文件，即可直接检查 Agent 准备执行的代码与文件变更，再决定允许或拒绝请求。该能力使工具权限审核从“确认将执行什么操作”进一步升级为“确认具体将改变什么内容”，提高源码操作的透明度与可审计性。

> **从记忆资产的数学自检、长上下文的一致性遍历，到恶劣网络渲染和代码变更审计，本次更新继续补强 VCP 在高负载、异常输入与高权限操作下的可靠性边界。**

### 2026-08-23 · VCPMessageRenderer V4：流式竞态治理、语义级 Div 岛识别与多应用对接

VChat 流式渲染器完成 V4 重构。本次升级不以增加更花哨的渲染能力为目标，而是集中治理流式输出中的竞态、终稿一致性、复杂内容隔离与长期运行资源回收，让现有流式体验更加稳定、可靠，也为后续维护和扩展建立更清晰的职责边界。

#### 流式时序与画面推进更加稳定

1. **进一步消除流式竞态问题**：重新梳理消息接收、逐步显示、最终渲染和历史保存之间的执行顺序，降低旧任务、重复事件及异步处理互相干扰的概率。
2. **流式显示更加稳定顺滑**：优化文本展示进度、渲染队列与帧调度机制。面对高速输出、长消息和复杂内容时，画面变化更加自然，同时减少无效计算。
3. **最终内容更加可靠**：流式预览结束后统一切换到规范终稿，并阻止后台旧任务继续修改最终画面，使 Markdown、公式、代码块、样式与富内容的最终结果保持一致。

#### Div 岛识别与复杂内容隔离增强

V4 大幅增强 Div 岛嵌套识别能力。即使 AI 在岛内输出任意未闭合或非规范嵌套的 `div`、`script`、`style` 等标签，也不会轻易破坏岛的作用域识别。渲染器由此能够实现接近语义级的 Div 动画块识别与作用域定向，为复杂动态内容提供更稳固的边界。

复杂内容的安全性与兼容性同步提升。新版进一步强化消息样式隔离、HTML 预览隔离和代码区域识别，避免代码示例被误判为真实网页内容，也降低单条消息中的样式影响整个聊天界面的风险。

#### 生命周期、保存状态与维护边界完善

1. **资源释放与长期运行稳定性提升**：完善动画帧、定时任务、预览窗口、工具结果缓存和异步渲染任务的清理机制，降低长时间聊天后的资源残留、后台空转与性能波动。
2. **消息保存状态更加明确**：优化流式消息结束后的保存流程；若保存失败，界面会明确标记消息尚未写入历史，避免用户误判保存状态。
3. **职责边界进一步收敛**：V4 更清晰地区分流式生产、界面投影、内容处理和历史保存，并补充相关回归测试，为后续功能升级提供稳定基础。

#### V4 内核完成多应用对接

VCPMessageRenderer V4 内核现已完成与 **V阅读、V论坛、V笔记和V文坊**的对接。多个内容与交流子应用可以复用统一的消息渲染能力，在流式处理、复杂内容展示、终稿切换、安全隔离和生命周期管理方面保持一致行为。

> **V4 是一次以消灭竞态、稳定性能和降低维护成本为目标的底层重构。日常使用方式基本不变，但流式输出在复杂场景、多应用协作与长时间运行下会更加可靠。**

### 2026-08-22 · VChat Chat Kernel 与公共服务核心重构

VChat 完成主聊天底层架构的系统性整理，并将内部 Post 服务独立为公共核心 **VCPAgentChatCore**。本次改造主要解决主聊天模块职责过多、局部修改容易牵一发动全身的问题；用户熟悉的操作方式基本保持不变，但聊天、工具等待、话题切换、多窗口协作和异常恢复获得更清晰可靠的运行边界。

#### VCPAgentChatCore 独立为公共 Post 核心

原属于 VChat 内部的 Post 服务现已独立为 VCPAgentChatCore，解除 ChatService 与主 Renderer 之间的直接耦合，并形成独立服务组。VCPAgentChatCore 作为所有子应用访问 VcpAgentPost 功能的公共通用核心，统一承载请求提交与服务对接，避免各聊天界面和子应用重复维护同类链路。

#### 主聊天职责拆分与统一 Chat Kernel

过去的主聊天渲染器同时负责流式传输、消息保存、界面渲染、话题切换、设置与主题、附件、语音、通知及辅助窗口等大量工作。上述职责现已拆分并交由边界明确的模块分别管理，降低局部变更影响整个聊天系统的风险。

新的 Chat Kernel 统一管理流式会话、运行状态、结束事件和消息提交，进一步明确界面渲染、实时状态与持久化历史之间的边界，避免同一条消息被不同模块重复保存或重复结束。

#### 流式身份隔离与多界面独立运行

1. **重试与迟到事件隔离**：每次流式请求均拥有独立身份和版本。旧请求产生的迟到文本、迟到结束事件或异步结果，不会再轻易混入新一轮重试消息。
2. **聊天界面运行环境独立**：主聊天、独立聊天窗口、VoiceChat、Rust Assistant 及其它辅助窗口分别使用自己的流式消费者与生命周期，不再隐式共享当前助手、当前话题或历史投影状态。
3. **Surface 生命周期完善**：每个聊天界面均拥有明确根节点与能力范围；事件监听、定时任务、观察器、异步任务和窗口订阅均支持重复安全释放，并能拒绝界面销毁后才返回的迟到结果。
4. **全局对象与兼容入口收敛**：清理已无生产消费者的旧聊天接口和历史读写兜底；仍需保留的公共接口拥有明确所有者及动态验证，减少全局对象被意外覆盖或多处争用。

#### 话题切换、历史读取与流式结束竞态修复

当 AI 正在等待 VCP 工具返回时，即使用户切换到其它话题，系统也会保留当前流式会话的临时快照。切回原话题后，尚未结束的回复可以恢复到聊天界面，不会再因历史重载而消失。

如果读取历史文件期间流式消息刚好完成，系统会核对读取前后的活动会话状态，避免较旧的历史文件结果覆盖或删除刚完成的消息。等待工具回执时的半成品请求仅保留在运行态，不会提前写入正式历史；既有 VCP 工具标记协议和最终消息保存规则保持不变。

### 2026-08-17 · 共笔文坊三态解耦、分页预览与动画源码快速定位

共笔文坊完成输入态、渲染态与源码事件态的三态解耦，并引入独立事务队列与稳定态仲裁机制；同时新增分页预览双页编辑和动画元素源码快速定位能力。本次更新重点解决三类状态相互追赶、重复对账所产生的竞态，以及 IME 中文输入法在组合输入期间容易受到渲染和源码同步干扰的问题，进一步提升复杂文档与动态演示的编辑效率。

#### 输入、渲染与源码事件不再互相阻塞

文档编辑链路现明确拆分为三个相互独立的状态域：

1. **输入态**：负责接收键盘输入、选区变化以及 IME composition 等尚未最终提交的交互过程。
2. **渲染态**：负责维护用户当前看到的文档结构与局部视觉结果，不再直接反向抢占输入过程。
3. **源码事件态**：负责把已确认的编辑动作映射为唯一真源上的源码事务，并追踪修订、区间与事件代次。

三类状态不再共享同一条即时写入链路，也不要求每次细微变化都立刻相互覆盖。由此，输入法组合文本、浏览器 Selection、局部 DOM 更新与源码映射可以在各自边界内推进，避免某一侧的临时状态被另一侧误判为最终结果。

#### 独立事务队列与合并提交

三个状态现在分别由独立事务队列管理。高频输入、连续删除、选区移动、局部渲染和源码事件会先在对应队列中排序、去重与合并，再以可验证的事务批次进入后续同步流程。

这种队列化设计减少了逐事件立即对账造成的重复编译、无效渲染和状态回写，也避免多个异步事件同时争夺同一修订。连续编辑因此可以被收敛为更少、更稳定的提交，而不是让每次按键都触发三态之间的连锁更新。

#### 仅在稳定态执行仲裁对账

三态同步不再以“最后到达的事件覆盖其它状态”为准，而是在输入、渲染和源码事务达到可确认的稳定边界后统一仲裁。系统会结合事务顺序、修订代次、源码区间与当前组合输入状态，判断哪些变化可以合并、哪些需要延后，以及哪一份状态能够作为本轮对账依据。

对于尚未结束的 IME 中文组合输入，渲染刷新和源码回写会尊重 composition 生命周期，不再提前拆分、重排或覆盖候选文本；待输入稳定后，相关变化再一次性映射到源码并触发最小范围渲染更新。这显著减少了中文输入中的丢字、重复上屏、光标跳动、候选中断与内容回滚问题。

此次重构进一步巩固了共笔文坊“渲染结果可直接编辑、真实源码保持唯一”的基础：三种状态可以独立演进，却仍会在稳定边界上收敛为一致结果，复杂文档中的连续输入、快速修改和中英文混合编辑因而更加流畅、可靠。

新增连续渲染态、分页展示态和源码编辑态之间的任意双页编辑。用户可以根据当前任务自由组合两个工作面，在连续编辑、分页预览和源码修改之间并行对照，既能观察文档的整体分页效果，也能直接调整对应源码。

新内核建立了独立的文档渲染、编译、编辑与运行时体系。它可以在接近记事本的直接编辑体验下，承载 Markdown、HTML、CSS、JavaScript 动画、LaTeX、Mermaid、SVG、Canvas、Three.js 及其它可编程内容的任意混合，并支持换行、输入、删除、复制、粘贴、圈选、粗体、斜体、字体、字形和排版等常规操作。无论文字来自普通段落、HTML、动态图形还是程序运行时，系统都尽可能允许用户在最终渲染结果中直接修改，同时精准落回原始源码，而不破坏周围未被触碰的内容。目前少量旧 UI 仍使用 V1 API，尚在继续对接 V3 内核。

#### 源码保持型渲染编辑管线

V3 不会把编辑后的 DOM 反序列化回 Markdown。混合编译器在生成阅读用 HTML 的同时，会为每个可编辑区域记录内容类型、源码字符起止位置、内容哈希、Markdown token 类型及可编程岛语义 ID。围栏代码、Mermaid、块级公式、样式块和可编程岛会在编译前被识别并保护，避免被 Markdown 编译过程吞并或重写。

连续编辑面平时保留完整的静态渲染树，以维持浏览器原生拖选、跨文字选择和右键行为；只有确认发生折叠点击后，被点击的局部区域才会切换为临时视觉编辑树。标题井号、列表与引用前缀、粗体和斜体分隔符、代码标记及 HTML 标签骨架并未从编辑模型删除，而是根据光标和选区上下文动态显隐。作者看到的是接近最终成品的排版，底层处理的仍是原始源码字符序列。

所有输入、Selection、中文输入法 composition、格式化、复制粘贴与结构插入都会映射为源码字符偏移。每次写入均以 `from`、`to`、`expected` 与 `insert` 组成区间事务，并在提交前复核原文、区间哈希、稳定原子边界与当前修订。映射过期、并发变化或边界不可安全编辑时，系统会拒绝写入，而不是覆盖未知内容。事务完成后仅重新编译和修补受影响区域；KaTeX DOM、Mermaid SVG、Canvas、动画样式、运行时节点、选框与拖拽手柄等派生状态永远不会被写回真源。

#### VDOCX 与 VPPTX：两类原生工程模型

Scriptorium 现在明确区分两类原生工程：

- **VDOCX**：面向文章和连续流富文档，以 `markdown-hybrid` 为正文真源。CommonMark / GFM、静态 HTML、LaTeX、Mermaid 与可编程岛可以长期共存，文档级样式独立保存为 `document-css`。
- **VPPTX**：面向演示和发布，采用独立的 HTML Scene 页面模型。每页保存完整的 HTML Scene source，可包含样式、HTML、依赖声明和内联脚本；演示共享样式保存为 `deck-css`，页面拥有稳定 ID、备注、资源、转场、时长、自由坐标对象和图层顺序。

混合源码工作面通过 CodeMirror 直接连接唯一真源：VDOCX 编辑 Markdown 混合源码，VPPTX 编辑当前页的完整 HTML Scene；CSS 工作面则分别编辑独立的文档样式或演示共享样式，避免样式伪装成正文节点。

#### 可编程岛与受管理文档运行时

VDOCX 新增稳定语义“可编程岛”，用于容纳需要脚本、Canvas、WebGL、局部样式、运行时依赖或长期身份的组件。每个岛拥有文档内唯一且稳定的语义 ID，编译器将整个岛视为稳定原子边界，使 Agent 能精确更新组件而不接触周围正文，也避免普通文本被随机永久 ID 污染。

系统为每个页面或岛建立可释放运行时，统一跟踪 `requestAnimationFrame`、timeout、interval、清理回调、Anime.js 实例、视口可见性和脚本生成节点。切页、重渲染、关闭文档或切换工作面时，持续任务会被停止并按序清理；离开视口的动画和媒体可暂停并在返回后恢复。Anime.js 与 Three.js 获得内置依赖支持，常见 CDN 声明会转换为本地固定依赖，未知公网脚本则保留审计信息并降级为不可执行声明。

#### 文脉协作：单文档即带署名的协作仓库

ScriptoriumCollaborator 让 Agent 以协作者而不是远程桌面操作者的身份参与创作。Agent 可以同时读取文档语义、真实源码和当前视觉截图，先理解“写了什么”，再检查“如何实现”，最后确认“看起来怎样”。

所有针对当前窗口文档的 Agent 写操作统一进入 PR 协议。提案携带作者、摘要、请求 ID、预期修订和最小源码变更；人类可在文脉面板同时审阅局部源码差异与隔离渲染差异，再决定允许、拒绝或填写回执。系统会在提交预检和实际批准两个时点检查文档 ID 与修订，并通过请求 ID 保证幂等，防止等待审批期间的人类新修改被旧提案覆盖。

文脉系统现将版本、作者、Agent 提案、人工审批、回执、快照和恢复记录放在同一条图形化历史中。协同署名面板新增 Agent 与用户头像，提升多人、多 Agent 场景中的身份识别度；历史界面还可回顾此前全部 PR 的代码变动及渲染变化动画。每个 VDOCX 或 VPPTX 因而都可作为自带作者系统、提交记录、双重差异审阅、审批协议、工程快照与安全回溯的协作仓库。多人可以分别带着自己的 Agent 团队加入同一作品，所有贡献仍汇入同一唯一真源和同一条可审计文脉。

历史回溯不会删除未来。系统会先为当前状态建立安全备份，再从目标节点的内嵌快照生成新的恢复记录，使“恢复”本身也成为可追踪事件。

#### 多模态、图形与字体编辑强化

VCP 原生文档现可嵌入任意类型多媒体。人类手动插入媒体时，链路会自动维护内容 Description、媒体来源、MIME、原生尺寸和时长等信息；Agent 通过超栈追踪管线插入资源时也会主动补充描述，方便其它 Agent 理解媒体含义、引用关系及其与动画时间轴的配合方式。

工作台新增快速图形创建与手绘多模态窗口，并支持图片和基础图形的拖拽、缩放、旋转、Z-index 图层布局及文字环绕。图形以 SVG 源码为真源，每个图形拥有独立根 CSS 容器，可通过图形化入口编辑 SVG 形状源码并添加对象级隔离 CSS；在 VPPTX 中还可继续配置动画脚本、时序对齐和页面交互。

字体与字形编辑交互得到大幅优化。针对 Chromium 原生无法识别部分旧式 family 格式字体的问题，系统会为不可识别字体自动建立影子字体并补充兼容的类型识别字段，从而改善老式系统字体的加载、选择和渲染表现。

#### ZIP 工程容器、资源封装与独立发布

`.vdocx` 与 `.vpptx` 现采用 Scriptorium v2 ZIP 工程容器，按职责分别保存清单、正文源码、独立 CSS、文脉节点、媒体、字体和 MIME 信息，而不是把整个工程塞进一个巨型 JSON。资源使用 SHA-256 内容寻址，可自动去重并在打开时校验路径、资源 ID 与实际哈希；编辑期间映射为生命周期受控的本地 URL，源码不再混入巨大 Base64。

工程还可封装 JavaScript 依赖、Python 服务、操作元信息及多人或多 Agent 协作历史。保存和导出使用临时文件原子替换目标，降低中途失败导致工程损坏的风险。导出 HTML 时会自动封装图片等多模态资源、固定脚本依赖并清除仅供内部编辑和协作使用的元信息，使成品可以独立阅读、放映和发布。

#### 四类工作面与沉浸模式

Scriptorium 现在围绕同一文档模型提供四类工作面：

1. **连续编辑**：直接操作编译后的 VDOCX 文稿或当前 VPPTX 场景。
2. **阅读 / 放映预览**：VDOCX 进入纸张分页阅读，VPPTX 进入逐页场景播放。
3. **混合源码**：直接编辑当前唯一正文或页面源码。
4. **CSS 源码**：独立编辑文档 CSS 或演示共享 CSS。

文档编辑界面新增沉浸模式。进入后会隐藏全部非必要 UI，仅保留纯粹的文字编辑与阅读空间，适合长时间专注写作。

此次 V3 重构把过去互相冲突的能力闭合到同一条链路：人类编辑最终渲染结果，修改精准映射回唯一源码；Markdown、HTML、CSS、公式、图表、媒体与程序运行时长期共存；Agent 同时理解语义、源码和画面，通过带署名、幂等与修订保护的 PR 参与协作；源码差异、渲染差异、审批、回执、快照和回溯则共同进入文脉。

> **一份文档可以同时是人类自然书写的成品、Agent 精确操作的源码、受控执行的程序、可独立保存的工程，以及拥有作者与审批历史的共同作品。**

### 2026-08-10 · VCP 原生文档与演示系统上线：从修补第三方编辑器转向建立自己的创作生态

8 月 9 日上线 VCPScriptorium 后，开发很快遇到了现实问题：原先采用的第三方 DOCX 编辑器大量基础能力并不完整，对非 ASCII 字体、中文排版、智能缩进和自然换行的支持也不可靠，字体边缘渲染效果同样难以达到正式产品要求。原本用于开发新功能的时间，有约三分之二被迫花在修补第三方底层问题上。

因此，VCP 在 8 月 10 日作出关键转向：**不再围绕第三方编辑器继续打补丁，而是开始建立自己的原生文档内核、文件格式、排版系统和发布生态。**

这次变化不只是“换一个编辑器”，而是重新划分人与 AI 在文档创作中的工作：

- **人负责内容**：直接修改文字、观点和创意，不必反复学习复杂排版操作。
- **AI 负责呈现**：从源码层处理布局、样式、润色、动画和视觉设计。
- **双方编辑同一份作品**：人编辑眼前已经渲染好的内容，AI 编辑背后的页面结构，两边的修改可以继续合并，而不是每次都重新生成一份无法维护的成品。

#### VDoc：文章和富文档的原生格式

VDoc 使用 `.vdocx` 扩展名，是 VCP 自己的富文档格式，支持两种内容模式：

1. **文档模式**：用于文章、报告、教程、方案和长篇内容。
2. **PPT 模式**：用于提案、课程、演讲和视觉化叙事。

用户可以像使用普通文档软件一样，直接在渲染结果中修改文字。文字编辑会尽量保持现有区块的布局和视觉结构；AI 则可以继续调整页面源码、版式、动画和整体风格。

#### VPPT：面向演示和发布的原生格式

VPPT 使用 `.vpptx` 扩展名，面向正式演示和播放。它以页面源码作为内容与视觉效果的最终标准，因此 AI 不只能改文字，还能直接调整整套演示的布局、转场、动画与导播界面。

导出的演示页面会自带 VCP 的 PPTX 导播器，包括播放控制、页面导航和翻页动画，可直接用于演讲、展示或独立发布。导播器本身也是作品的一部分，可以继续由 AI 定制。

#### 保存后直接用浏览器打开：阅读器与编辑器正式解耦

这套系统最直观的用法，可以用一个简单例子说明：

1. 用户打开 VCP 的 Scriptorium 文档中心。
2. 直接点击导入一个 `.docx` 文件，原文档约 99% 的排版都能被保留下来。
3. 点击保存，得到一个 `.vdocx` 文件。
4. 双击这个 `.vdocx` 文件，或者把它拖进浏览器，就能直接打开阅读。

浏览器中看到的不是一张被拉长的普通网页，而是一份拥有完整分页的 DOCX 布局文档。纸张尺寸、页边距、分页、页眉页脚和打印结构都会由文件内置的分页渲染框架负责还原，阅读体验和真正的 DOCX 文档一样。

这意味着文档阅读器已经与 Scriptorium 编辑器解耦：创作者可以在 Scriptorium 中编辑和保存，接收者不需要安装 VCP，也不需要打开编辑器，只用浏览器就能阅读最终文档。`.vdocx` 既是可以继续编辑的 VCP 原生文档，也是可以直接分发和打开的独立网页成品。

`.vpptx` 的使用方式相同：用户可以导入 PPTX，在尽量保留原排版的基础上继续编辑，然后保存为 `.vpptx`。接收者直接用浏览器打开，就会进入文件自带的 PPTX 导播器，通过播放控制、页面导航、翻页动画和转场效果观看完整演示，同样不依赖 Scriptorium 或传统演示软件。

VDoc 和 VPPT 也可以另行导出为标准的独立 HTML 文件：

- VDoc 导出的 HTML 内置 DOCX 风格分页渲染框架，仍然保持按页组织的正式文档布局。
- VPPT 导出的 HTML 内置 PPTX 导播器、翻页控制和页面转场动画，可以直接用于演讲、展示和网页发布。
- 导出时会自动去掉只用于 VCP 内部编辑、协作和管理的元信息，只留下最终阅读、播放和发布需要的内容。

#### 导出 PDF：为打印和正式交付准备

文档和演示均可导出 PDF。导出过程会固定富媒体内容和选定的动画画面，尽可能把动态作品的关键视觉结果保留到静态页面中，方便打印、归档和正式交付。

#### 样式中心与自研排版引擎

VCP 同步建立统一样式中心。标题、正文、卡片、图表和演示主题都可以保存为可重复使用的样式模块，在不同作品间导入、分享和复用。用户可以选中内容后直接套用样式，AI 也可以基于已有样式继续扩展设计。

原生文档还开始接入 VCP 自研字体与排版优化引擎，用于处理中文字体、字间距、段落节奏、缩进、换行和页面布局，逐步摆脱浏览器默认排版与第三方渲染器的限制。

#### 富内容与动画进入同一套文档架构

VCP 原生文档支持把图表、公式、流程图、富媒体、脚本图形和动画直接放进文档或演示中。动画不再是外挂播放器效果，而是可以和文字、图片、图表及页面布局一起保存、编辑、发布和导出。

系统同时支持导入已有的 DOCX 与 PPTX 文件。DOCX 导入后约 99% 的原有排版可以被保留，内容还可以继续编辑、重新排版，并直接保存为可在浏览器中打开的 VCP 原生作品。这样既保留现有办公文档的迁移入口，也让阅读和播放摆脱对专用办公软件及 Scriptorium 编辑器的依赖，不再让未来的创作能力受传统文件结构限制。

从 8 月 9 日的“接入一个 DOCX 编辑器”，到 8 月 10 日的“建立原生文档、演示、样式、动画与发布体系”，VCPScriptorium 的定位已经发生根本变化：它不再只是 VChat 里的文档子应用，而是 VCP 人机协同内容生产生态的统一工作台。

> **人决定表达什么，AI 负责让它更好地被看见。**

### 2026-08-09 · VCPScriptorium 首次上线，AI 原生文档共建开始落地

经过约 16 小时集中开发，VChat 全新子应用 **VCPScriptorium** 上线首个可用版本。这个版本最初基于第三方 DOCX 编辑与渲染组件搭建，目标是先跑通“人和 AI 共同编辑同一份文档”的完整流程。

首版已经接入 VCP 的底层能力，让 Agent 可以理解文档、执行自然语言编辑、保存编辑时间线和恢复点，并参与排版与内容调整。文档可保存为普通 DOCX，也可保存为 VCP 扩展文档；扩展格式能够使用 VChat 的高级富渲染能力，在文档中呈现流程图、公式、动画区块、脚本图形和富媒体内容。

这一天验证了方向：文档不应只是 AI 生成后交给人下载的静态附件，而应该成为人和 Agent 可以持续理解、修改和完善的共同工作空间。

但首版也暴露了第三方底层的明显限制。它能帮助快速证明产品思路，却不足以承载中文长文、精细排版和稳定发布。这个问题直接推动了第二天的范式转变：从“在现有 DOCX 编辑器上增加 AI 功能”，转向“由 VCP 自己定义文档格式、渲染内核和完整生态”。

### 2026-08-06 · 插件热重载事务体系重构，VCPAgentWebCore 公共内核与全局健康自检上线

本次更新围绕插件运行时治理、模型思维链适配、Agent 网页操作底座和系统配置可靠性，对 VCP 后端基础设施进行了新一轮解耦与统一；VChat 前端则继续强化多 Agent、多话题并发流式输出下的渲染稳定性与内存生命周期管理。

#### Plugin.js 热重载与统一事务管线

后端中央 **Plugin.js** 管理器完成多类型插件热重载架构重构，将插件配置、变量状态与运行时实例拆分为相互独立的管理边界，使配置变更、变量更新和运行时重载不再彼此捆绑。系统现在能够分别追踪三类状态之间的依赖关系与更新代次，并在热加载过程中按需刷新对应部分，减少全量重载带来的状态污染、资源抖动和并发竞态。

本次重构同步新增两条核心基础管线：

1. **统一事务提交管线**：插件产生的内存变更统一进入事务入口，由中央管线负责合并、排序、提交与回收，避免不同插件直接竞争共享状态。
2. **PluginWatch 管线**：统一追踪插件源码、配置、变量与运行时变化，并将高频更新收敛为可控的热重载事务。
3. **队列化合并与内存事务管理**：针对大量插件在同一时刻密集提交状态的场景，对重复或关联变更进行队列化聚合，降低事件风暴、重复提交与瞬时内存压力。
4. **高并发插件交互优化**：重点改善 Cron 等调度场景下数千个静态插件同时递交内存事务时的吞吐与一致性，为后续万级插件并发交互奠定基础。

#### VCPAgentWebCore 公共网页智能内核

**VCPChromeBridge V3** 的底层引擎已独立解耦为公共依赖 **VCPAgentWebCore**。新版内核不再局限于单一 ChromeBridge 插件，而是以可复用模块的形式向任意后端服务、插件及 Electron 应用提供完整的 AI—网页理解与操作能力；VCPChromeBridge V3 则作为其浏览器桥接实现之一继续工作。

VCPAgentWebCore 统一提供以下能力：

- **页面发现与自然语言操作**：支持页面结构发现、内容理解、模糊命令解析与自然语言驱动的网页操作。
- **CDP 与权限分级**：提供 Chrome DevTools Protocol 控制能力，并对网页信息、浏览器操作和敏感数据实施分级授权。
- **可靠性验证闭环**：对目标可用性、指令执行过程和页面变化结果进行检查，降低“动作已发出但实际未生效”的误判。
- **页面 Hash 签名与变化追踪**：为页面状态建立 Hash 签名，持续追踪内容、结构、导航上下文及其差异。
- **语义句柄动态重定向**：页面结构变化后，可通过 JavaScript 将既有语义句柄动态重定向至新的有效目标，提升连续操作的鲁棒性。
- **输入与环境仿真**：支持键鼠及文本输入模拟，并可仿真设备指纹、网络指纹和不同访问环境。
- **导航上下文 Diff**：跟踪页面跳转、标签切换和连续导航中的上下文变化，为跨页面任务保留可验证的操作链路。
- **强化 Html2MD 与多模态语义翻译**：内置增强版原创 Html2MD 算法，并强化图片、音频、视频及复杂页面结构的自然语义识别与翻译。
- **Electron 对接模块**：内置标准 Electron 集成层，使桌面端子应用和其它 Electron 模块可以直接复用同一套网页智能内核。

随着公共内核完成拆分，网页发现、理解、控制、验证与安全治理不再需要由不同模块重复实现，ChromeBridge、Loom 及后续网页类 Agent 能力可以在一致的底层协议上持续演进。

#### VCP 占位符全局健康自检

### 2026-07-15 · 浪潮 V9.2 四层测地线算法重构

V9.1 已经能够将候选记忆的有序 Tag 视为穿越查询能量场的路径，但仍会把精确事实、语义路线、主题共振和正文一致性压缩进同一个测地分数。一条宽泛但平滑的主题路径可能因此获得接近明确事实锚点的排序权，而短小却高度准确的记忆也可能因路径样本不足得不到应有提升。V9.2 为解决这一问题，将测地线读出重构为“四层几何”：

1. **直接层**：判断候选是否真正接触查询的核心事实，包括高势能精确 Tag，以及由多个独立查询锚共同确认的强语义接触。
2. **结构层**：检查候选 Tag 链是否构成连续、方向合理的语义走廊，避免由彼此孤立的热点拼成虚假路径。
3. **主题层**：衡量整篇记忆是否持续处于查询唤醒的能量区域，并抑制公共词、枢纽 Tag 和偶然擦边形成的主题晕轮。
4. **闭合层**：验证 Tag 路径最终能否回到候选正文，并比较原始查询与浪潮增强查询对正文的解释力，确认增强带来了正向语义提升。

四层证据不会被简单相加。系统会根据查询的逻辑深度、信息熵、共振强度、覆盖率、新颖度和语义深度，动态决定本次检索更应信任事实、结构还是主题，再由闭合层完成最终验收。候选仍需先通过原有节点场证据守卫，四层几何只能在可信证据基础上补足排序权限，不能仅凭正文相似或向量提升凭空创造奖励。精确身份锚点也必须同时满足高查询势能、Tag 特异性与 Tag—正文闭合度，公共词和传播产生的涌现节点无法冒充直接事实。

不同证据拥有独立的奖励上限：直接事实可以进行较强纠偏，结构路径获得中等权限，主题相关只能小幅微调；辅助几何采用“补足奖励地板”而非重复叠加奖励，避免同一证据被多次计分。浪潮现在不仅能发现“名称不同但沿同一条记忆河道相连”的内容，还能进一步判断它属于查询事实的直接延伸、连续且有方向的推理或叙事路径、整体主题共振，还是由公共词与局部相似制造的假通路。这使短而精准的事实记忆更容易得到保护，完整的跨 Tag 语义路径更容易被识别，宽泛主题造成的误提升则被明显压低；内测跑分、自动化对照、AI 主观评分与用户反馈均获得明显改善。

当查询能量场过窄、熵过低、候选覆盖不足、路径缺乏区分度，或全部候选都未形成可信接触时，系统仍会完整回退到原始近邻顺序。每次排序变化都会记录直接、结构、主题、闭合、方向一致性、向量提升、证据类别、奖励上限和实际增益，使候选前移能够追溯到具体 Tag 路径与证据层级。

LightMemo 对照模式同步升级，可同时展示原始近邻、关闭测地线的浪潮结果，以及启用 V9.2 四层测地线后的结果，并给出候选所属证据层、接触 Tag、路径连续性、闭合质量、方向一致性、身份锚保护和最终测地增益。开发者可以直接观察哪些记忆被移动、移动了多少，以及变化来自事实命中、结构路线、主题共振还是正文闭合验证。
